# HexxlaDB General Audit — May 2026

General audit of the codebase for correctness, performance, scalability, and
concurrency opportunities. Items are rated by severity and grouped by type.

---

## 🔴 High Priority

### A1 — `AscendRange` reads header on every call

**File:** `internal/engine/btree.go:AscendRange`

`BTree.AscendRange` calls `t.eng.ReadHeader()` on every invocation to retrieve
`BTreeRoot`. Every `QueryCells`, `SearchCells`, `HealthCheck`, `StatsMVCC`,
secondary index scan, and `PruneCellVersions` issues a `pread(page0)` per
`AscendRange` call. Read-only transactions already carry `cachedBTreeRoot`
(set from the atomic `db.cachedHdr` at transaction open) but `Tx.AscendRange`
at `tx.go:263` delegates straight to `btree.AscendRange`, discarding it.

**Fix:** Add `BTree.AscendRangeFromRoot(root uint64, from, to []byte, fn)`.
Wire `Tx.AscendRange` to call it with `tx.cachedBTreeRoot` when `!tx.writable`.
`leftmostLeaf(root, from)` already accepts a root parameter — minimal change.

**Impact:** Eliminates N `pread(page0)` calls per read transaction, where N is
the number of index scans in that transaction (typically 3–10 for QueryCells).

---

### A2 — `Compact` issues a single monolithic write transaction

**File:** `compact.go:compactCopy`

All keys from source are copied in one `Update` callback, producing a single
WAL commit of unbounded size. For a 100 MB database with 4 KB pages this is
~25,600 page writes in one WAL record burst. It also holds `db.mu.Lock()` for
the entire duration, starving all readers.

**Fix:** Batch by key count (e.g. 4096 keys per commit) inside `compactCopy`,
releasing the lock between sub-batches. Pattern already established by
`PruneCellVersions`.

**Impact:** Reduces peak WAL burst, allows concurrent readers during compaction,
prevents WAL file from bloating during a large compact.

---

### A3 — No freelist; overflow pages leak until `Compact`

**File:** `internal/engine/overflow.go:freeOverflowChain`

`freeOverflowChain` is an explicit no-op. Every `DeleteCell` or `PruneCellVersions`
that removes an overflow value leaks the overflow page IDs permanently. For
delete-heavy MVCC workloads the file grows unboundedly until the operator runs
`Compact`.

**Fix options:**
1. **Deferred freelist:** Record freed page IDs in a `free/` keyspace; at the
   next `writeOverflowChain`, pop IDs from the freelist before bumping
   `NextPageID`. Increases write path complexity.
2. **High-water hint in header:** Track `WastedBytes uint64` in the header;
   expose it on `StatsMVCC` so operators know when to compact.
3. **Auto-compact trigger:** If `WastedBytes > X% of file size`, surface a
   warning via `HealthCheck` and document the compact workflow.

Option 3 (observability) is low-risk and sufficient for v0.x. Option 1
(proper freelist) is the right long-term fix.

## 🟡 Medium Priority

### A4 — `Update` reads header for `CommitSeq` baseline

**File:** `tx.go:126`

`db.eng.ReadHeader()` is called at the start of every write transaction to get
`hdr.CommitSeq` as the `readSeq` for read-your-writes. `db.cachedHdr.Load()`
already has this value. Since `writeSeqNext.Add(1)` provides the write sequence
independently, the `ReadHeader` call serves only to set `tx.readSeq` — which
could come from the cache instead.

**Fix:** Replace `db.eng.ReadHeader()` in `Update` with `db.cachedHdr.Load()`
for `readSeq`, matching what `View` already does.

---

### A5 — `cachedHdr` refresh after commit still calls `ReadHeader`

**File:** `tx.go:187`

After `CommitWriteTxn`, `Update` calls `db.eng.ReadHeader()` to refresh
`cachedHdr.BTreeRoot`. The engine could expose `BTreeRoot()` directly from an
internal atomic (the root is updated by `UpdateHeader` — already written to
disk) or `UpdateHeader` could return the new `Header`. Eliminates one
`pread(page0)` per write transaction.

---

### A6 — `ViewAtTime` scans all commit-time keys forward from origin

**File:** `tx.go:resolveReadSeqAtOrBeforeUnixNano`

`CommitTimeScanBounds(unixNano)` returns `[minKey, asOf]` and the function
scans forward, keeping a running maximum. On a busy DB with millions of commits
this is O(commits before asOf). The correct approach: scan backwards from `asOf`
and stop at the first (highest) key — O(1) for the common "current time" case.

**Fix:** Implement `BTree.DescendRange(from, to, fn)` — reverse leaf walk using
`prev` links already present on `leafData`. Wire `resolveReadSeqAtOrBeforeUnixNano`
to descend from `asOf` and return the first hit.

**Impact:** `ViewAtTime` with a recent `asOf` is currently O(total commits).
After fix: O(1) for current-time queries, O(k) for historical where k is
commits from asOf to present.

---

### A7 — `StatsMVCC` allocates a full `map[PackedCoord]struct{}` for `LogicalCells`

**File:** `mvcc_lifecycle.go:StatsMVCC`

Builds a map of all distinct coordinates to count them. With 1M cells this
allocates and GC-pressures a 1M-entry map. Keys are already sorted by coordinate
in the B+ tree — the same `prev-coord` pattern from `PruneCellVersions` applies:
count a new logical cell whenever `p != prevCoord`.

**Fix:** Replace the map with a running `prevCoord` and a `logicalCount` counter.
O(1) extra memory.

---

### A8 — `HealthCheck` scans `cell/` keyspace twice

**File:** `health.go:HealthCheck`

Calls `db.StatsMVCC()` (acquires `RLock`, scans all `cell/` keys) then opens
`db.View` (acquires `RLock`, scans all `cell/` keys again via `healthScanCells`).
Two full B+ tree range scans of the same keyspace in sequence.

**Fix:** Compute `MVCCStats` inside the same `View` callback as `healthScanCells`,
merging the two scans into one. Emit `LogicalCells` and `VersionedRows` directly
from the health cell scan.

---

### A9 — `scoreCell` re-lowercases tags on every invocation

**File:** `search.go:scoreCell`

Allocates `tagsLow []string` and lowercases every tag on every record scored.
For a `QueryCells` scan of 1000 cells with 10 tags each: 10,000 `strings.ToLower`
allocations in the hot path.

**Fix options:**
1. Store tags lowercase at write time in `PutCell` (normalise at ingest).
2. Pre-lower tags once in `Tx.scoreRecord` before calling `scoreCell`.

Option 1 is a schema change (existing tags are mixed-case). Option 2 is safe and
localised to the query path — move the lowercase loop into `scoreRecord` and pass
`tagsLow` into `scoreCell`.

---

### A10 — `CompactTo` opens source with a 4 MiB page cache

**File:** `compact.go:CompactTo`

Opens source DB with full `Open()` including default page cache. A sequential
read-once compaction scan is the worst case for CLOCK-Pro: every leaf page is
read exactly once and then evicted, warming the cache with data never reused.
Net effect: 4 MiB of RAM consumed, zero cache benefit.

**Fix:** Pass `&Options{PageCacheSize: -1}` (cache disabled) when opening the
source in `CompactTo`. Note: currently `CompactTo` passes through `opts` from
the caller — it needs to clone `opts` and override `PageCacheSize`.

## 🟢 Low Priority / Quality

### A11 — `sortResults` uses deprecated `sort.Slice`

**File:** `query_exec.go:sortResults`

Uses `sort.Slice` throughout. `slices.SortFunc` (Go 1.21+) avoids the indirect
closure call overhead and is the idiomatic modern form. Minor but consistent with
the `modernize` linter directive in `.golangci.yml`.

---

### A12 — No `BatchDeleteCells` API

**File:** (new, `batch_delete.go`)

`BatchPut` exists (`batch_put.go`) for bulk ingest. There is no equivalent for
bulk delete. The MVCC prune path batches internally, but callers wanting to delete
a known set of cells have no single-call entry point — they must loop over
`DB.Update` manually. Already tracked in `TODOS.md`.

---

### A13 — `hasAllTags` / `hasAnyTag` use `slices.Contains` — O(tags × required)

**File:** `search.go:hasAllTags`, `hasAnyTag`

Linear scan per tag. At typical production sizes (≤20 tags, ≤5 required) this
is not measurable, but documented for completeness. A sorted-binary-search
approach would help if tags-per-cell ever exceeds ~50.
